# 根据关联 Requisition 判断岗位项目标记

## 两种不同的依据

- **岗位／项目标记**：用户要求按目标岗位所属项目分类时，根据已核实关联的 requisition、岗位职责或实际项目任务内容，判断岗位的项目工作类型，然后对用户授权范围内属于该岗位的申请处理其相应的 Moka 候选人项目标记。此标记表示该候选人申请与该项目的关联，不等于证明此人已具备或完成该项目的全部能力。
- **Taxonomy v1.1 的 Project Category 能力分类**：继续按候选人的简历、项目经历、Note、评估等个人证据判断实际能力，并与 v1.1 当前批准规范词表匹配；不可只凭岗位职责、候选人进入某一招聘阶段或岗位被贴标，就断言个人能力、履历、评估结论或 Tier。
- 不同实际组中的标签即使名称相近也是不同字段。`Agent Workflow Evaluation` 如在 Moka 的手动项目标签组中，则按该组的真实名称和 ID 处理；v1.1 中 `agent workflow and trajectory evaluation` 是 Project Category 的规范词条，不能仅凭字面相近就声称两者的组别、ID、发布状态或治理口径相同。需要判断两个标签的个人能力适用性或正式跨库映射时，应分别取证并核实。

## 操作和语义判断

1. 精确定位用户指定的职位、招聘阶段和目标申请，核对职位标识、职位名称和申请归属。进入 Moka `Positions → Job requisitions` 或授权接口，读取与该职位**实际关联**的 requisition 以及该职位本身的 JD；在关联列表或系统返回中核对对应职位。按可见字段记录岗位 ID、需求 ID/编号、关联来源、页面位置和读取时间。不把名称相似、业务部门、国家、历史任务或搜索结果当作关联证据；如没有稳定 ID，以当前界面可复核的唯一岗位与关联记录为依据，歧义仍然暂停。
2. 同一需求关联多个职位时，对每个目标职位分别检查是否真的属于该需求并阅读其角色职责。若职位有多个需求，核实当前申请适用的需求及职位特定职责；无法确定适用关系或资料互相冲突时，不默认套用其他职位或全部需求的标签。无权访问、没有绑定记录、仅显示标题或缺少工作内容时，说明缺口，不硬猜。
3. 提取并逐字引用与岗位实际交付相关的职责、任务、工作流或评估过程，结合项目名、职位 JD 和当前启用标签含义进行语义匹配，并简述原因。不要只靠职位名称、一个关键词、地区或项目名机械推断；有多个独立且证据充分的项目类型，可多选。不要把通用软件开发、单纯使用 AI、设计 agent 或孤立的代码审查自动等同于 agent 工作流评估。
4. **示例（虚构，非固定职位映射）**：岗位任务要求设计 coding agent 的评测准则，评估其在真实工程场景中的多步骤操作，并审查包含命令、工具调用、代码改动与结果的完整执行轨迹；这些具体任务支持岗位项目标记 `Agent Workflow Evaluation`。即使原文没有逐字出现完整标签名称，也可依据完整任务语义得出结论；仅出现“Coding Expert”、只写“使用 AI 工具”，或只涉及 agent 开发而不涉及评估，均不足以得出该结论。
5. 核实当前租户 Moka 标签库中匹配值的真实分组、精确名称、Active 状态及系统 ID，核对用户授权范围及该岗位各候选人的身份和完整旧标签。已有相同值跳过；当前未创建/未启用、关联不明、不同值冲突、权限不足或语义不确定时保留现状并单列原因。不要创建新标签、自动删除旧标签、未经授权将候选人级标签写到无关申请，也不因一例适用而给所有相似岗位固定贴同一标签。
6. 若用户授权写入，先按适用门控验证真实来源、关联、项目标签、身份及已有标签；提交前重读。写后重新打开候选人档案核验所有原标签和新增值。若标签由候选人档案共享，核查已知关联申请的显示情况，说明该标记会显示于共享记录，不把它误认为各岗位均经过独立分类。只输出建议时不写回。离线校验不证明语义、权限、关联真实性或执行成功。

## 手动项目标记写回校验

有明确写入授权时，按 `scripts/validate_requisition_marker_plan.py` 文件头中的契约，为每个候选人准备私有 `plan`、`context` 和当前 `library`，然后运行：

```bash
python3 scripts/validate_requisition_marker_plan.py --plan PLAN.json --context CONTEXT.json --library LIBRARY.json
```

匿名默认阻断样例见 `templates/requisition-marker-plan.example.json`、`templates/requisition-marker-context.example.json`、`templates/requisition-marker-library.example.json`；不能把示例内容或虚构标识当作生产证据。计划中的岗位任务引用必须是目标职位或实际关联 requisition 工作内容的连续原文；语义是否匹配由执行者判断并说明，脚本不自动认定语义。用户限定招聘阶段或具体人员时必须列出受授权的申请，不可冒充全岗位范围。旧标签、系统 ID、启用状态、来源、关联和共享范围均须据实核查；不能因页面载入失败将旧值视为空。校验器默认要求采集快照不超过 60 分钟，可按实际观察使用 `--max-age-minutes`（上限 1440 分钟），但较宽窗口不替代提交前重新读取。`add` 与已有值的 `skip` 不允许删除其他标签。

若实际编辑对象是候选人档案，关联的其他岗位申请可能只因共享而显示相同标签：记入影响清单并向用户说明，但不额外编辑这些申请或把其视为独立岗位分类。申请级编辑不可宣称影响其他申请；候选人、关联或共享关系无法核实、用户明确禁止共享影响时暂停。

## 输出

每条建议记录：职位与 requisition 标识、关联证据、原文摘录和来源位置、项目标记的实际 Moka 组/值、语义理由、已有或拟添加、受影响申请范围及例外。个人简历、Notes、招聘需求正文与候选人清单放在私有任务目录，不写入技能或通用示例。
